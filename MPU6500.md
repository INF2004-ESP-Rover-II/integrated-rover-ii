# GY-6500 / MPU6500 integration

The Sensor Pico uses one MPU6500 on GP6/GP7. The Arduino
`gy6500_reader.ino` has been ported to Pico SDK C in `mpu6500.c` and
`imu_filter.c`, with continuous sampling in `imu_sampler.c`; no Arduino core or Wire library is needed. The old LSM303
accelerometer/magnetometer driver, configuration and magnetometer telemetry
fields have been removed.

## Wiring and mounting

Connect the module to the **Sensor Pico**:

| Module | Connection |
| --- | --- |
| VCC | 3V3 |
| GND | GND |
| SDA | GP6 (I2C1) |
| SCL | GP7 (I2C1) |
| AD0 | GND, selecting address 0x68 |
| CS / NCS, if exposed | 3V3 to select I2C mode |
| INT | Unconnected |

ToF remains on a separate bus: **I2C0, SDA GP4, SCL GP5**. The old left
ultrasonic assignment on GP6/GP7 is disabled, so it cannot initialize or trigger
the IMU pins. Its packet distance is 500 (unavailable), with ultrasonic status
bit 2 set. Front, back and right ultrasonic channels keep their existing pins.
To restore the left channel, assign unused GPIO and enable `ULTRA_LEFT_ENABLED`
in `sensor_config.h`; the config rejects overlap with the IMU pins.

Use 3.3 V power and I2C pull-ups to 3.3 V. A module with AD0 high needs
`MPU6500_ADDR` changed to `0x69` in `sensor_config.h`. This integration reads
one MPU6500. It checks WHO_AM_I for the MPU6500 value 0x70.

Keep the **rover level and stationary through startup**. Heading uses the first
sample's gravity direction as the rover's initial vertical axis, and projects
all three gyro components onto it. This supports fixed flat, sideways or tilted
IMU mounting for turns on a level floor. `MPU6500_YAW_SIGN=-1` makes clockwise
turns increase heading. The IMU must stay rigidly attached to the rover.

Pitch/roll still describe the sensor axes. For the existing pitch-based slope
compensation to describe rover nose-up motion, mount **+X forward, +Y left,
+Z up**; flat pitch is then near zero and nose-up pitch is negative. Automatic
yaw alignment does not establish the robot's forward axis or remap pitch/roll.
Gravity projection assumes turns about the startup vertical axis; it is not a
full attitude quaternion solution for arbitrary three-dimensional motion.

## Startup and data

Keep the rover stationary through startup. After an extra one-second settling delay,
the driver measures up to ten 100-sample windows (about one second each),
accepts the first stable window, and subtracts its mean gyro offset from later
readings. The extra attempts let startup handling settle; the quality limits
below remain unchanged. Transfer failure aborts calibration. Every accepted window requires
acceleration magnitude 0.85–1.15 g, gyro standard deviation at most 0.35 deg/s,
gyro peak-to-peak variation at most 2 deg/s, and acceleration variation at most
0.08 g on each axis. A mean bias above 20 deg/s on any axis is rejected.
These are provisional engineering quality gates, not accuracy specifications.

A steady offset above 5 deg/s can now be measured instead of causing immediate
failure on a single sample. It raises a warning retained in the System Ready
summary: the MPU6500 specification lists initial zero-rate tolerance as +/-5
deg/s at 25 C, so a larger measured offset is suspicious. Verify the rover is
stationary and that heading stays still after boot. This calibration cannot
distinguish constant yaw rotation from gyro bias; it must only run while stopped.
It does not prove that a sensor with a large bias is healthy. Ten rejected
windows leave the IMU offline until restart. USB Serial Monitor is optional;
firmware does not wait for it.

Initialization resets the still-powered IMU, wakes/enables its axes, configures
both ranges and low-pass filters, and reads back ACCEL_CONFIG/GYRO_CONFIG.
Expected values are 0x08 (accel +/-4 g) and 0x18 (gyro +/-2000 deg/s). It waits another 100 ms after configuration before calibration so
the first output is not a cached sample from the previous range. A first-sample
value near 2 g can be consistent with default +/-2 g data decoded using the
new +/-4 g scaling, but does not establish that cause by itself. A persistent
2 g magnitude is still rejected. Window logs show gyro X/Y/Z means, maximum
standard deviation, gyro/acceleration spans and acceleration magnitude range;
the driver does not silently rescale acceleration or widen its magnitude gate.

Accelerometer range is +/-4 g; gyro range is +/-2000 deg/s (16.4 LSB/deg/s).
After init/calibration and SD startup, core 1 exclusively reads the IMU on
I2C1 and runs fusion at a target of 100 Hz. Core 0 handles ToF on I2C0,
ultrasonic timeouts, SD and UART. Main-loop packets copy a synchronized snapshot
without an I2C read. Packet rate is nominally 20 Hz and can decrease while core 0
is busy; heading acquisition continues independently. Late worker deadlines
are counted instead of replaying artificial catch-up samples.

The complementary filter adjusts tilt weighting using actual elapsed time,
equivalent to the sketch's 0.98 weighting at 10 ms. Heading integrates the
bias-corrected gyro vector projected onto startup gravity, wraps into [0, 360),
and starts at zero on the first valid worker sample. It is relative to startup,
not magnetic north, and drifts. A small negative drift appears near 360 degrees
(e.g. 359.2 means -0.8 degrees). A real half turn should produce approximately
180 degrees on a level floor. There is no magnetometer or implemented ArUco
heading correction.

`[IMU RATE]` reports measured worker frequency, maximum gap, read errors,
missed deadlines, near-full-scale events, heading, all gyro axes and the
startup gravity unit vector. Target frequency is about 100 Hz with about 10 ms
between samples. Main-loop blocking may delay the diagnostic print but not
normally the worker. Near-full-scale corrected gyro values (>=1970 deg/s on
any axis) latch an IMU fault to avoid presenting a clipped turn as valid heading.
The margin accounts for bias subtraction near the ADC limits. Snapshot age
must be at most 50 ms for a healthy packet.

Read failures produce `imu_status = 1` rather than replaying a healthy snapshot.
Reads can recover on the next cycle. A gap of more than 500 ms between successful
fusion samples latches an IMU fault until restart because rotation during that
gap is unknown. The existing rover heading freshness gate then expires. This
does not change the project's existing manual-without-heading setting.

Startup failures are repeated as `IMU startup:` and `IMU bus:` in the System
Ready summary, including the last device identity read. These remain visible
when the serial monitor misses the earlier detection/calibration messages.
`WHO_AM_I=0x00` alongside a read failure is the initialized placeholder, not a
successfully read identity. Calibration rejection summaries retain the measured means and variation,
so the cause remains visible even if USB misses the earlier window messages. Runtime transfer failures and recovery are
reported separately from the latched >500 ms sampling gap.

`[TOF DIAG L/F/R]` distinguishes I2C ready/result/interrupt-clear failures from
rejected range statuses and includes the raw distance. Diagnostics are limited
to one message per sensor every two seconds. All three sensors initializing
(`mask=0x07`) does not guarantee later valid ranges. `--` is unavailable;
fault bits L/F/R = 1/2/4 mean offline or no accepted result for more than 300 ms.
Front ToF urgency drives `stop=YES`; unavailable data does not assert that
detector output, and `stop=NO` is not evidence of a clear path.

The UART packet includes roll and is **59 bytes** after removing the three
magnetometer floats (previous integration: 71 bytes). Both packet
declarations and checksum paths match. **Flash both boards together; mixing old
and new firmware is incompatible.** Existing ToF distance and obstacle flag
packing is unchanged. MQTT `imu` now contains:

```json
{
  "accel": {"x": 0, "y": 0, "z": 9.81},
  "gyro": {"x": 0, "y": 0, "z": 0},
  "heading": 0,
  "pitch": 0,
  "roll": 0,
  "heading_reference": "startup",
  "status": 0
}
```

Acceleration uses m/s², gyro uses deg/s, and angles use degrees. The dashboard
displays heading, pitch and roll, hiding angles when IMU status is an error.
Rotation commands do not modify measured heading in dashboard odometry.
The rover's legacy forward slope compensation now uses zero flat pitch and
negative nose-up pitch, instead of the old 77-degree baseline. Failed IMU
packets do not apply slope compensation.

## Build, flash and check

### IMU-only isolation image

For persistent calibration instability, build the separate diagnostic:

```sh
cmake --build build --target imu_only_diagnostic
```

Flash `build/firmware/sensor_pico/imu_only_diagnostic.uf2` to Sensor Pico.
This image initializes only the MPU6500 on GP6/GP7 and USB serial. It skips
calibration, heading, core-1 sampling, UART telemetry, ToF, ultrasonic and SD
setup. It prints uncalibrated acceleration/gyro samples, then mean, standard
deviation, min/max and span for each axis over 100 attempted reads. It repeats
WHO_AM_I and range register reads every window so resets/configuration changes
or transfer errors remain visible. It never labels noisy data as valid heading.

For electrical isolation, power off first and leave only the IMU connected to
Sensor Pico (3V3, GND, GP6 SDA, GP7 SCL, AD0 GND; CS high if exposed). Power
Sensor Pico through USB and keep the sensor resting securely on the table for
10–15 seconds without touching it. Capture several consecutive
`[IMU ONLY WINDOW]`, `[IMU ONLY AXIS]` and `[IMU ONLY NORM]` groups. The groups
are useful even if the serial monitor misses the initial banner.

If readings settle in this configuration, investigate the integrated setup,
connected power loads, vibration and wiring. If they remain unstable, the
remaining suspects include the IMU module, its power/connections and the IMU
driver; the result alone does not prove which is responsible. A steady gyro
offset and large time-varying readings are different faults. Do not solve the
latter by widening calibration gates. Restore the normal Sensor Pico UF2 after
testing; this diagnostic does not feed the rover/dashboard.

### Normal rover firmware

Build from the repository root with the project's configured Pico toolchain:

```sh
cmake --build build --target sensor_pico mecanum_robot
```

Flash `build/firmware/sensor_pico/sensor_pico.uf2` to Sensor Pico and
`build/firmware/robo_pico/mecanum_robot.uf2` to Robo Pico using BOOTSEL. Keep the
rover stationary during the next boot. Inspect Sensor Pico USB output for the
calibration message and `MPU6500: ONLINE`, then check near-zero flat pitch/roll,
negative pitch when raising the nose, and increasing heading on a clockwise turn.

Native driver/filter tests (Visual Studio x64 developer prompt):

```bat
cl /nologo /std:c11 /W4 /WX /I tests\imu_stubs /I firmware\sensor_pico\include tests\test_mpu6500.c firmware\sensor_pico\src\mpu6500.c firmware\sensor_pico\src\imu_filter.c /Fo:build\ /Fe:build\test_mpu6500.exe
build\test_mpu6500.exe
cl /nologo /std:c11 /W4 /WX /I tests\imu_stubs /I firmware\sensor_pico\include tests\test_imu_sampler.c firmware\sensor_pico\src\imu_sampler.c firmware\sensor_pico\src\imu_filter.c /Fo:build\ /Fe:build\test_imu_sampler.exe
build\test_imu_sampler.exe
python tests\test_dashboard_heading.py
python tests\check_obstacle_transport.py
python tests\test_dashboard_tof.py
python tests\test_marker_mapping.py
python tests\test_dashboard_safety.py
```

The simulated tests cover register setup, signed sample decoding/scaling,
calibration and rejected movement, transfer errors, tilt initialization,
time-dependent filtering, yaw direction/wrap, roll wrap, 64-bit sample time and
latched timing faults. The sampler test runs the real worker loop with a
simulated clock while the main consumer remains idle for an entire 180-degree
turn, and covers sideways mounting, read failures, saturation and overruns.
The dashboard regression ensures rotation commands preserve measured heading.
The transport check exercises actual sender/receiver
declarations, checksums, gyro/roll JSON values and all 1024 obstacle flag
combinations. These do not establish hardware accuracy or timing.

Register/scaling reference: [TDK MPU6500 register map](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6500-Register-Map2.pdf).
I2C timeout reference: [Raspberry Pi SDK hardware APIs](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html).

Gyro zero-rate tolerance reference: [TDK MPU6500 product specification](https://product.tdk.com/system/files/dam/doc/product/sensor/mortion-inertial/imu/data_sheet/mpu-6500-datasheet2.pdf).

A recorded IMU-only run had stable gyro means around X=2.65, Y=18.28 and
Z=1.34 deg/s, with eight of eleven complete windows meeting the existing
calibration gates and zero reported transfer errors. This demonstrates that
stable calibration data can be obtained in that tested setup. It does not
establish the cause of earlier unstable integrated-startup readings. The large
Y offset still raises a warning; it is measured anew at boot, never hardcoded.
